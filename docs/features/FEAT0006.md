# FEAT0006 — Implement Manager Workflow

## Goal

Implement the Manager-driven end-to-end runtime workflow that integrates puzzle discovery, Solver execution, Executor-based validation, persistence, concurrency, process lifecycle, diagnostics, and failure handling.

The purpose of this feature is to establish a correctly functioning integrated workflow.

It is not the final project-solving acceptance gate.

## Scope

Manager must implement the global workflow required to:

* discover project puzzles;
* determine which puzzles currently require Solver work;
* preserve required chapter/puzzle ordering;
* launch the appropriate Solver;
* manage Solver process lifecycle;
* enforce configured maximum Solver concurrency;
* receive submitted Solver candidates;
* perform full-dataset candidate validation using Executor;
* distinguish validation PASS, FAIL, and infrastructure ERROR;
* return failed-case information to the active Solver after normal candidate failure;
* persist `.solve` state after successful full validation;
* advance a chapter after successful validation;
* apply the persisted puzzle-status eligibility and transition rules defined by `REQUIREMENTS.md`, including correct solve/skip behavior and the `re-solve` to `pending` transition after successful replacement validation;
* coordinate runtime IPC;
* manage validation work without unnecessarily blocking unrelated chapters;
* implement graceful stop;
* propagate fatal errors using fail-fast behavior;
* produce appropriate Release/Debug diagnostics and run summaries.

Validator may exist as a logical step, helper, wrapper, worker operation, or other implementation structure.

It is not required to be an independent architectural subsystem if direct Executor-based full validation is simpler.

## Persistence

Manager owns authoritative `.solve` persistence after successful full validation.

Diagnostic reports may be written by the producing component or delegated to Manager, provided the same diagnostic event is not persisted redundantly.

Original `.a2b` puzzle data and authoritative Rules remain runtime-read-only.

## Process and Concurrency Behavior

The implementation must support the architecture's chapter-level Solver isolation and maximum-concurrency model.

Validation work must not make Manager perform expensive synchronous execution that prevents unrelated runnable work from progressing.

Manager owns the process trees it creates and must handle their normal and abnormal lifecycle appropriately.

## Failure Behavior

Normal candidate failure must return useful failed-case information to the corresponding Solver so solving can continue.

Infrastructure failures that make results untrustworthy must propagate according to fail-fast behavior.

Graceful owner interruption must stop active work safely where practical and preserve useful diagnostics.

## Verification

Verification must demonstrate that the Manager-driven end-to-end workflow functions correctly from its normal entry point.

Tests may use controlled Solver behavior, test fixtures, real implemented Solvers, or a combination as appropriate.

The workflow should exercise representative paths including:

* puzzle discovery and dispatch;
* Solver startup;
* candidate submission;
* Executor-based full validation;
* validation PASS;
* validation FAIL and feedback return;
* `.solve` persistence;
* puzzle/chapter advancement;
* status-based solve/skip behavior;
* successful `re-solve` candidate replacement and automatic transition to `pending`;
* concurrency/process handling;
* ERROR propagation;
* graceful stop;
* diagnostics and final summary.

## Acceptance Boundary

**FEAT0006 acceptance is not final project acceptance.**

FEAT0006 does not require that a complete real `solve all` run successfully solve every puzzle.

During feature verification or owner review it is acceptable for integrated execution to expose:

* puzzles that integrated execution reveals the current algorithms cannot reliably solve;
* Solver capability limitations;
* algorithmic failures that do not indicate a Manager workflow defect;
* other issues outside FEAT0006 scope discovered through integration.

A known defect in the Manager workflow itself remains a FEAT0006 acceptance blocker.

Such observations do not by themselves mean that the Manager workflow is invalid.

FEAT0006 acceptance concerns whether the integrated workflow behaves correctly.

After FEAT0006 and all preceding features are accepted, the project enters owner-driven integrated solving/testing. Problems discovered there are fed back to Codex and corrected iteratively until the final project completion criteria are met.

## Acceptance

FEAT0006 is ready for owner review when:

* the Manager workflow is implemented end to end;
* representative workflow paths have been verified;
* applicable tests/checks pass;
* Codex self-review finds no unresolved Manager-workflow defect within feature scope.

Final feature acceptance belongs to the owner.

Final **project** completion remains governed separately by `REQUIREMENTS.md`.
